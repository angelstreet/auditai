# 0011 - Cross-team synergy detection (M13, FR-14)

- Status: Accepted (first slice)
- Date: 2026-10-17
- Deciders: maintainers
- Related: [0003](0003-postgres-migrations-and-rls.md), [0007](0007-ai-pipeline.md), [0008](0008-auditor-review.md), [0009](0009-opportunity-register.md)

## Context

M9 built the AI pipeline that produces one approved `analyses` row per submission, with the themes carried inside `payload_json`. M10–M11 surfaced those analyses to the auditor and shipped the opportunity register. What is still missing for FR-14 is the _cross-engagement_ read: spotting that the same maturity theme (e.g. "source-checking practice", literacy axis) recurs across two or more engagements in the same tenant, and turning that recurrence into a follow-up interview prompt for the next round.

M13 splits that into the smallest verifiable slices:

- **Slice A (this PR):** `synergies` table + RLS, the `Synergy` contract, the `synergy.detect` audit-log action, and the ADR. Schema + types only — no worker yet.
- **Slice B (next PR):** the `detectCrossTeamSynergies(tenantId)` worker in `services/ai`, idempotent upsert on `synergy_key`, audit-log row per new detection, smoke test.
- **Slice C (later PR):** admin page to surface detected synergies (`/admin/engagements/[id]/synergies` or similar) and link them to the underlying analyses.

This ADR covers Slice A and captures the data shape and the RLS posture.

## Decision

### 1. The `synergies` table

```
synergies(
  id, tenant_id, axis ENUM, theme_label, synergy_key,
  source_analysis_ids JSONB, source_engagement_ids JSONB,
  occurrence_count INTEGER >= 2,
  proposed_followup_prompt TEXT,
  status ENUM ('detected' | 'surfaced' | 'dismissed' | 'archived'),
  detected_at, surfaced_at NULL, dismissed_at NULL,
  created_at, updated_at,
  UNIQUE (tenant_id, synergy_key)
)
```

- **One row per recurrence**, not one row per pair. If the same theme recurs across N engagements
  in the same tenant, we get one row with `source_engagement_ids = [...]` of length N
  (`occurrence_count = N`). The unique index on `(tenant_id, synergy_key)` makes the worker
  re-runnable without duplicating rows.
- **`synergy_key`** is a stable lowercase hash of `(axis, theme_label)`. The worker generates it
  with `crypto.createHash('sha1').update(${axis}|${theme_label.toLowerCase()}).digest('hex')`,
  then `synergyKeySchema` validates it on insert. No UUIDs here — keys are deterministic.
- **Privacy:** the row carries only ids + a short follow-up prompt. No answers, no respondent
  pseudonyms. `proposed_followup_prompt` is generated by the worker from the theme summary + the
  axis, never from free-text answers (which never reach the theme extractor — `extractThemes`
  groups by axis only).
- **Status lifecycle:** `detected → surfaced/dismissed → archived`. Soft transitions live in the
  table; no hard delete. The RLS policy keeps `DELETE` to service accounts only.
- **RLS:** standard tenant-scoped four-policy pattern, identical to M10's `analyses` table. The
  worker's `detectCrossTeamSynergies` runs under `app.is_service_account = 'on'`, which the RLS
  policy honours for reads/writes inside one tenant.

### 2. The contracts

`@auditai/contracts` adds `synergySchema` + `synergyWriteSchema` + `synergyIdSchema` (branded UUID) +
`synergyStatusSchema` + `synergyKeySchema`. The audit-log contract picks up a new `synergy.detect`
action and a `synergy` target kind. The discriminated `synergyAuditLogSchema` matches the same
pattern as the existing `analysisAuditLogSchema` / `opportunityAuditLogSchema`.

7 new tests in `synergy.test.ts`, 1 new test in `auditLog.test.ts`.

### 3. What is NOT in Slice A

This slice deliberately does not include:

- The detection worker (`detectCrossTeamSynergies`).
- The smoke that runs the worker end-to-end.
- A `synergies_data.json` synthetic seed in migration `0009` (next migration).
- An admin/UI surface.

Each of these arrives in its own small slice + PR so CI signals are tight.

## Consequences

- The data model is in place and tested. The next PR can land the worker in isolation.
- RLS posture is identical to the existing `analyses` table, so reviewers do not need to learn
  a new permission model.
- The `synergy.detect` audit-log action means every detection event has a `created_by` actor and a
  payload, matching the M10 + M11 pattern.
- The unique `(tenant_id, synergy_key)` index caps write contention even if the worker is run
  concurrently for the same tenant.

## Alternatives considered

- **One row per (engagement, theme) pair.** Rejected: turns a 2–3 engagement recurrence into a
  join problem. One row per recurrence is the simplest read surface and matches the way the
  auditor thinks ("this theme keeps coming back").
- **Store the synergy inside `analyses.payload_json`.** Rejected: synergies cross engagements;
  `analyses` is per-submission. A separate table is the right boundary.
- **Hard delete on dismissal.** Rejected: the audit trail (PRD §25.4) is append-only; soft state
  transitions + a service-account DELETE mirrors the opportunity register.
- **Use the existing `theme_count` counter on `analyses` for detection.** Rejected: that counter
  is per-row, not cross-engagement. Synergies need a derived view across rows; that is a worker,
  not a column.

## Slice B (this PR update)

The Slice-A schema gives us a destination; Slice B is the worker that fills it.

### 1. The migration `0009_synergy_audit_constraints.sql`

The audit_log table came online in M10 with a `CHECK` constraint on `action` and
`target_kind`. The CHECKs only allowed `analysis.*` and `opportunity.*`. This migration
drops and recreates each CHECK to also accept `synergy.detect` on `action` and `synergy`
on `target_kind`. Forward-only; no data rewrite.

### 2. The worker `detectCrossTeamSynergies(tenantId)`

Located in `services/ai/src/synergyDetector.ts`, the worker:

1. Loads every approved analysis for the tenant (`approved_at IS NOT NULL`) and pulls
   the themes out of `payload_json`.
2. Groups themes by `synergyKeyFor(axis, label)` — a deterministic SHA-1 hex of
   `axis|lower(label)` — and folds the contributing analysis + engagement ids into the
   group.
3. Filters to groups that cross **at least two distinct engagements** with **at least two
   distinct analyses** (the minimum definition of "cross-team").
4. For each qualifying group, UPSERTs one `synergies` row on `(tenant_id, synergy_key)`
   and writes one `audit_log` row with `action='synergy.detect'`, `target_kind='synergy'`,
   and the worker actor in `actor_user_id` (a synthetic auditor by default).

The worker is **purely additive** and **idempotent**:

- The unique index on `(tenant_id, synergy_key)` collapses repeats.
- On conflict, the JSONB arrays are recomputed as the union of previous + new ids, so a
  re-run never inserts a duplicate and never shrinks the source set.
- `detected` and `reused` counters in the return value make the smoke output machine-checkable.

### 3. The synthetic test (the smoke)

`apps/web/scripts/m13-smoke.mjs` is the only place the test creates a second engagement in
tenant A. It exists precisely so the existing `admin-engagements.spec.ts` anchor (one row
visible per tenant, 5/12 and 3/9) is preserved. The smoke inserts a fresh `'closed'`
engagement + submission + 2 approved analyses on a shared literacy theme, runs the worker
via `pnpm --filter @auditai/ai run synergy-smoke`, asserts the synergies row + audit_log
row, re-runs for idempotency, asserts `reused >= 1`, then cleans up. After the smoke the
seed is back to its single-engagement-per-tenant shape.

### 4. New unit tests

`services/ai/src/synergyDetector.test.ts` covers the pure parts of the worker (key
derivation, JSONB merge, group aggregation, the single-engagement-group drop). Five new
tests; the cross-engagement write path is covered by the integration smoke.

## Consequences

- The M13 detection loop is now end-to-end: analyses → worker → synergies row → audit_log
  row. Re-running the worker is safe and converges.
- The audit-log CHECK constraint is wider; the action / target_kind enums in
  `@auditai/contracts` (already extended in slice A) match the constraint.
- The smoke creates + tears down its second engagement atomically, so the M6 admin-tests
  anchor (1 visible engagement per tenant) still passes in CI.
- Slice C (the admin/board surface for synergies) lands next.
